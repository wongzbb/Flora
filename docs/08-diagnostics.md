# 预测、诊断与双重控制

双重控制在这里指一个真实行动既推进任务，又为以后采用哪段程序提供信息。它不是两个 LLM 角色互相对话，也不是给模型加一个“信息增益”打分提示。

## 诊断是带续行的程序

编译 bundle 中一个诊断包含以下字段：

```json
{
  "id": "inspect_current",
  "program": {"version": 1, "entry": "main", "blocks": {}},
  "inputs": {},
  "forecasts": [
    {"candidate_id": "old", "predicate": {"op": "eq", "path": ["start"], "value": 840}},
    {"candidate_id": "new", "predicate": {"op": "eq", "path": ["start"], "value": 900}}
  ],
  "witnesses": [{"start": 840}, {"start": 900}]
}
```

这是字段示意，空 blocks 不是有效 IR。完整可运行实例在 calendar 教程中。诊断必须先到达一个已开放工具的效果请求，并且含有实际续行。模型不能只写“建议查询”而省略查询后怎样处理。

`forecasts` 中候选 ID 必须存在且不能重复，最多三个。`witnesses` 最多八个，装的是假想的成功返回值，不是状态信封。内核会自行包成 `{"status":"returned","value":...}` 在 hypothetical VM 中检查续行。

## 何时获得正诊断分数

必须同时成立：

1. 至少有两组去重后的不同预测。
2. 谓词规则能够机械证明一对预测不能同时为真。
3. 提供的假想值分别满足这对预测。
4. 同一个诊断续行在两份假想值上产生不同的有效后续边界。

不同请求、不同纯返回，或一边发生具体故障而另一边到达有效边界，可以构成区别。两个故障、未解决的未知或相同续行结果不能制造正分数。

分数是“满足上述条件的预测组对 / 全部预测组对”。它不是概率、预期收益、任务奖励或世界模型。重复相同预测不增加分母中的独立组，也不能靠复制候选抬高分数。

## 保守的互斥证明

当前支持的充分规则包括：同一路径的不同 `eq` 常量、同一常量的 `eq` 与 `ne`、不相容的类型、一个谓词与其否定，以及在 `all / any` 结构中安全传播的互斥关系。

例如 `x < 3` 与 `x > 10` 实际互斥，但当前保守证明器不必认可所有这种情况。无法证明互斥只意味着得不到这部分诊断分数，不意味着二者确实重叠。

这项取舍让实现不依赖 SMT 求解器或任意可执行谓词。以后可以扩大证明规则，但必须保持“证明不了就不计分”的方向。

## 调度优先级

| 条件 | 选择 |
| --- | --- |
| 正常候选的请求全部相同 | 提交公共正常请求 |
| 诊断额度不允许，或没有正分诊断 | 默认正常候选；不存在时按稳定 ID |
| 多个正分诊断 | 分数最高者 |
| 正分诊断同分 | 优先与正常请求相同者，再按稳定 ID |
| 胜出诊断请求与正常候选相同 | 选择匹配正常候选，实际执行一次并共享观察 |

运行时负责诊断额度：两个正常动作之间最多插入一次独立诊断，任务级额度由配置限制；独立诊断还要求至少剩余两次工具调用额度，保留一次后续正常推进的机会。诊断与普通动作消耗同一工具和模型预算。没有已知奖励函数时，本版本不会推测“冻结其他候选”的机会成本。

## 一个确定性调度示例

```python
from flora.scheduler import choose

def frontier(ident, tool, kind="normal", score=0.0):
    return {"id": ident, "request": {"tool": tool, "args": {}},
            "kind": kind, "score": score,
            "anchor_epoch": 0, "anchor_digest": "a" * 64}

frontiers = [
    frontier("first", "act_one"),
    frontier("second", "act_two"),
    frontier("inspect", "read_current", "diagnostic", 1.0),
]
assert choose(frontiers, "first") == "inspect"
assert choose(frontiers, "first", diagnostic_allowed=False) == "first"
```

这段代码只选择 ID，不调用工具。实际运行的分数来自 `evaluate_diagnostic`，不能由模型在 bundle 中随意提交。

## 真实反馈的范围

`check_forecasts()` 要求实际事件 ID、请求和历史前缀都与选中的诊断匹配。相同参数的另一次分页调用不能当作这次诊断的反馈。调用者应从已校验的 trace store 取得真实事件，而不是传任意字典。

预测结果 `PASS` 只说明这条本次预测与这个实际返回一致；`FAIL` 只说明该预测被反驳；`UNKNOWN` 表示无法判断。它们都不是程序正确性分数，也不会自动写入消费者合约的通过证据。

实际返回超出全部预测时，保留这些失败或未知结果，并继续运行诊断自己的真实续行。不要把返回强制投到最接近的假想值。

## 假想数据的隔离

假想 VM 状态保留 `mode="hypothetical"`，效果执行器拒绝这种模式提交外部动作。诊断报告带有 `hypothetical: true` 和 `contract_evidence: false`。将假想计算输出作为观察写入真实 trace 是违反执行边界的行为。

假想值能够说明“如果收到这个值，代码会怎样分支”，不能说明该值在环境中可达，也不能说明它有多大概率出现。这也是本版本分数被称为结构辨别指标的原因。
