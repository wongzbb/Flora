# 术语、设计取舍与来源

## 术语表

| 术语 | 在本项目中的具体含义 |
| --- | --- |
| 未决程序 | 仍保留多个候选内部实现的程序 |
| IR | 受限制的、JSON 编码的中间语言 |
| 纯计算 | 只基于显式已有值计算，不调用宿主或改变外部环境 |
| 效果 / effect | 通过已注册工具产生的一次真实外部请求 |
| 边界 / boundary | 解释器暂停并向宿主返回控制的位置 |
| 续行 / continuation | 收到结果后执行的块和显式捕获的局部值 |
| 默认候选 / incumbent | 没有合格诊断时优先继续的正常候选 |
| 历史锚点 | 当前 epoch 与 trace digest 的组合 |
| 回执 / receipt | 实际效果事件的记录，不含假想输入 |
| 合约 / contract | 关于具体程序和消费者的局部可执行检查及适用证据 |
| 适用规则 / guard | 从通过、失败、未知样本中综合的有限经验条件 |
| 预测 / forecast | 对某次查询返回的可检查假设 |
| 诊断 / diagnostic | 为辨别后续程序行为而提出、并带有实际续行的工具动作 |
| 双重控制 | 一次行动既推进当前任务，又提供修订程序所需的信息 |
| 反驳 | 实际观察与限定范围的预测不一致 |
| 冻结 | 当前真实路径使旧续行失去执行资格；不等于观察反驳 |
| UNKNOWN | 信息、支持的语义或计算资源不足，不能得出通过或失败 |
| interrupted_unknown | 工具可能已产生效果，但本地没有可靠的最终结果 |

## 为什么采用 JSON IR

目标是让暂停、比较、保存与检查具有清晰语义。任意 Python 代码可能通过导入、对象方法、属性访问或闭包产生隐藏效果。用独立 IR 可以把宿主访问集中到工具边界，把值和控制流限制为可检查对象。

这不是对 Python 使用者的限制性编程建议：工具适配器本身仍然可以用普通 Python 实现。限制的是模型生成的程序以及需要在不接触外部世界时运行的计算。

## 为什么合约只做局部承诺

在缺少真实世界模型、任务 oracle 和任意重置的条件下，无法自动证明任意 agent 程序正确。局部消费者检查则能够诚实地回答：“在这份实际输入上，程序有无定义”“这次改写是否保持下一边界”“这段引用是否确实来自指定观察”。

这些检查比纯格式校验更强，但仍有边界：相同下一请求可能共享同一个错误；有限样本上的规则不能自动推广到所有新输入。规则负责选择检查对象，局部执行负责确认当前情况。

## 为什么保留 UNKNOWN

把不可判断归为失败，会错误丢弃可能有效的程序；把不可判断归为通过，会制造证据。单独保留未知可以准确区分不支持的数据、没有取得的工具结果、纯计算超限和实际反例。

## 为什么不是概率模型

候选程序不是从已知分布抽样的世界模型。相同错误可能被不同候选重复表达，候选数量也会受编译器输出风格影响。因此，默认诊断评分是去重后的可检查分歧指标，不声称后验概率、预期奖励或最优信息价值。
