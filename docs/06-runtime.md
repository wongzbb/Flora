# 运行时与候选生命周期

运行时是连接纯程序、真实工具和证据记录的协调层。解释器只能提出请求；运行时判断是否在正确的历史位置提交，并保证程序不会因为内部比较而偷偷执行外部动作。

## 候选与默认程序

一个编译 bundle 包含正常候选、默认候选和可选诊断。默认候选负责在没有有效诊断时推进任务。候选由固定模型提出，并不代表真实世界的概率分布。候选之间也可能共享同一个错误。

初始 bundle 中的每个程序带有自己的入口输入。运行时把它转为机器状态，进行纯计算，直到效果请求、返回、错误、未知或内部候选分叉。

## 什么情况下共享一次调用

共享必须同时满足：处于同一 epoch、绑定同一 trace digest、工具标识相同、参数可以可靠比较且完全一致。只比较人类可读描述不够，两个“看起来相同”的请求可能操作不同对象。

共享是一次当前事件的多个消费者，不是跨时间缓存。`next_page()` 连续调用两次通常意味着取不同页面。运行时必须把它们记为两个事件，即使参数字典都为空。

## 谁能继续执行

| 发生的事件 | 候选状态 | 下一步 |
| --- | --- | --- |
| 实际请求与候选等待请求匹配 | 可以恢复 | 将同一次真实 outcome 交给该续行 |
| 实际请求与候选等待请求不同 | 暂停或冻结 | 不得使用旧续行发出下一动作 |
| 纯指令失败 | 内部故障 | 记录操作和输入见证，供修订 |
| 纯运行资源不足 | 未知 | 调整资源或重新编译，不能证明候选错误 |
| 产生最终返回 | 完成候选 | 由运行时的最终返回规则处理 |

冻结候选仍然可以作为下一次编译的参考代码，但它的旧机器状态不能继续操作已经变化的环境。

## 历史锚点

`epoch` 标识已登记的真实效果位置；`trace_digest` 标识该位置对应的具体事件内容。只有数字相同不够：两个不同的历史都可能发生过五次调用。

编译 bundle 必须回显 `expected_epoch` 和 `expected_digest`。内核拒绝过期锚点，避免耗时模型响应到达时覆盖更晚的状态。修订程序也必须从当前真实历史重新建立状态。

## 重新编译不是自动回滚

需要新程序时，编译器获得原任务、实际事件、当前内部数据、旧代码和具体报告。它输出新的剩余程序，再经过完整校验。运行时不会让旧世界复活，不会自动撤销工具动作，也不保证模型重新编译一定成功。

每次编译、格式修复和诊断均消耗预算。编译失败时保留具体错误；没有可执行候选且没有剩余编译预算时，运行以未完成结束。

## 纯运行的界限

`fuel` 限制单次内部执行工作量；`max_value_bytes` 限制值的规模。有限制的纯运行用于避免无限循环、大容器和过量计算，并不会证明算法在所有输入上终止。

`read_receipt` 与 `read_memory` 只读取宿主明确传入的视图。解释器不会枚举文件系统、浏览网络或读取模型供应商环境变量。需要这些行为，必须在任务权限内注册显式工具。

## 正常结束与失败结束

一个 IR `return` 表示程序自己返回，不自动表示任务成功。成功指标来自任务原本提供的评估方式。运行结果应同时检查：运行是否完成、是否有未决外部效果、返回值是什么、消耗了多少预算，以及任务环境是否给出了成功反馈。

普通工具异常可以成为程序处理的数据；预算耗尽、取消和无法确认效果状态的中断不能用普通“错误分支”绕过去重试。遇到状态未知应先核实已发生的真实动作。
