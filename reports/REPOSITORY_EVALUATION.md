# 公开仓库编码验收

日期：2026-09-28（Asia/Shanghai）。使用用户授权网关声明的 `deepseek-v4-flash`；不独立鉴定上游模型身份。

## 任务与验收标准

来源：[more-itertools](https://github.com/more-itertools/more-itertools)，MIT 许可，固定提交 `4998a257373f36e91edef7324572ed8df10f39d1`（v10.5.0）。原项目 817 项 unittest/doctest 通过，其中 1 项跳过。

8 个任务包括 6 个人为植入的回归和 2 个明确要求的新 API。每个任务从独立提交和干净检出开始，固定运行完整测试套件；每个初始任务都已确认测试失败。它们是在真实项目上构造的开发验收集，不是真实用户 issue、官方 benchmark 或盲测成功率。

外部验收检查完整套件、任务专属边界输入、原测试哈希、原检出状态和补丁可应用性。新 API 还检查公共导出、类型声明存在与语法、文档入口和迭代消费边界；没有运行完整静态类型检查器。独立验收程序位于模型工具不可读的工作区外，不作为在线工具或正确答案注入。

## 发现与对应修改

1. 通用搜索只读取每个文件前 64 KiB，实测无法找到位于 more.py 第 3804 行的 is_sorted。Coding Agent 应用层加入 `search_code` 和 `read_lines`，扫描完整有界文件，只把相关行送入模型，并沿用现有路径保护与完整文件哈希。
2. 源码和测试整段进入上下文增加成本。编码指令引导先定位、再读取窗口、使用受哈希保护的局部替换，并提醒不要用窗口覆盖全文件。
3. 未完成时的 CLI 原先没有清楚解释原因。现在显示失败原因、累计用量与保留必要参数的恢复命令；预算耗尽和未知工具结果各给出对应处理提示。
4. 已保存会话保持原工具集合与原指令绑定。既有真实 API 会话在无需网络请求的情况下重开成功。

修改前保留两个诊断运行：strict 分块任务因 IR 不合法失败，排序任务因输入预算耗尽失败。修改后 strict 分块首次完成；排序仍未完成，因此不把两例结果概括为普遍性能提升。

## 尚未解决的限制

主要剩余失败来自模型输出截断、JSON 标点结构错误、IR 字段/控制流校验失败，以及累计预算耗尽。扩大重试没有稳定解决这些问题。现有验证器拒绝非法程序，既有回执被保留，但模型仍可能无法完成最终总结。

本轮说明代码导航和失败反馈已经改善，也说明当前模型配置下的整体编译可靠性仍不足以宣称工业级编码成功率。后续应针对输出协议的可靠生成、上下文重复和编译修复做受控实验。

本轮没有修改双重控制、合约、运行时或编译器实现；没有运行与 ReAct/OpenHands 的公平比较或消融，不声称验证了双重控制的性能增益。

## 调用与费用边界

每个任务的配置：最多 10 次模型调用、60 次工具调用、240,000 输入 token、60,000 输出 token、420 秒运行预算；单次输出预留 8192、HTTP 超时 90 秒、格式修复上限 1。使用低推理强度和 JSON object 请求配置。

全部 8 项及两项旧实现诊断运行，累计 **65 次模型调用、86 次工具调用**，服务报告输入 **1,414,720**、输出 **295,740** token，未知用量调用 **0**。恢复阶段用量已含在会话累计值中，没有重复相加。

输入 token 以服务返回的用量记账，一次请求的实际输入可能让累计值超过阈值；运行时随后停止，不再发送下一次请求。未拿到该网关的账单与计费单价，因此不估算金额。

公开仓库源码与任务文本是本轮模型可见的数据；用户业务源码、私有 Flora 源码及凭据未作为模型文件工具输入。测试脚本、原始轨迹、响应正文和凭据不进入仓库。
